1.1 CHAPTER OVERVIEW
---------------------
This chapter documents the full technical implementation of the Adorix AI Kiosk system, a smart, 
context-aware advertising platform designed to revolutionize digital advertising experiences. 
The system comprises two repositories:

  1. adorix-project  – The AI-powered in-store kiosk (hardware/software)
  2. adorix-webb     – The web-based management platform (dashboard, campaigns, analytics)

Together, these form a cohesive ecosystem where businesses can manage, monitor, and deliver 
intelligent, personalized advertisements to real-world customers.


1.2 OVERVIEW OF THE PROTOTYPE
-------------------------------
The Adorix prototype is a dual-repository system:

  [KIOSK SYSTEM – adorix-project]
  A standalone touchless AI kiosk that:
    - Continuously plays ad content in Loop Mode (State 1)
    - Detects viewer age/gender via camera and switches to a Targeted Ad (State 2)
    - Allows the user to say "Hey Adorix" to begin a full AI conversation (State 3)
    - Answers product-specific questions using a hybrid QA Engine + TinyLlama LLM
    - Returns to Loop Mode when interaction ends

  [WEB PLATFORM – adorix-webb]
  A Next.js web application that:
    - Provides a business dashboard with analytics and performance metrics
    - Allows users to manage ad campaigns via the Campaign Studio
    - Uses Supabase for cloud data storage and Clerk for authentication
    - Sends real-time ads and metadata to the kiosk over the internet

  Key Integration:
    - Supabase is the shared cloud database. The web platform uploads ads and sets rules,
      and the kiosk backend syncs periodically via the /api/sync endpoint.

1.4 IMPLEMENTATION OF THE BACKEND COMPONENT
---------------------------------------------

[adorix-project Backend – FastAPI Python]

  Location: /adorix-project/backend/main.py
  Entry Point: uvicorn main:app --host 0.0.0.0 --port 8002

  Key Architecture: AdorixStateManager class that manages:
    - system_id: 1 (Loop), 2 (Personalized), 3 (Interaction)
    - Vision thread: continuously runs camera and processes faces
    - Wake word thread: listens for "Hey Adorix" in background
    - WebSocket connections: broadcasts state to React frontend
    - Interaction loop: manages TTS/STT conversation

  Key API Endpoints:
    GET  /            - Health check
    GET  /api/ads     - List available ad files
    POST /api/sync    - Pull latest ads from Supabase
    WS   /ws          - Real-time bidirectional state communication

  Module Structure:
    modules/ad_engine/     - Rules-based ad selector + demographic mapping
    modules/interaction/   - STT, TTS, Brain (LLM), and Interaction loop
    modules/vision/        - OpenCV face detection models
    modules/wake_word/     - Sherpa-ONNX wake word detection
    modules/storage.py     - Supabase sync logic
    modules/analytics.py   - Session data recording

[adorix-webb Backend – Express.js]

  Location: /adorix-webb/backend/src/
  Entry Point: server.js → app.js

  Architecture: Standard MVC (Model-View-Controller):
    routes/      - Defines API endpoints (auth, user, contact)
    controllers/ - Handles request logic
    services/    - Business logic and external API calls
    middlewares/ - Auth guards, CORS

  Key API Routes:
    POST /api/contact     - Handles contact form submissions (nodemailer)
    GET  /api/auth        - Authentication routes (Clerk integration)
    GET/PUT /api/user     - User profile management (CRUD)

1.6 IMPLEMENTATION OF THE DATA SCIENCE COMPONENT
--------------------------------------------------

  [Vision & AI Pipeline – adorix-project]

  This is the core data science component:

  1. FACE DETECTION (Hardware Input)
     File: backend/vision_service.py
     - OpenCV DNN (SSD model) detects faces in each webcam frame
     - Confidence threshold: 60%. Runs at ~10 FPS
     - On detection: crops face region + sends to DeepFace worker thread

  2. DEMOGRAPHIC ANALYSIS (DeepFace)
     - DeepFace.analyze() runs in a background thread to avoid blocking
     - Extracts: age (numeric) + dominant_gender (Male/Female)
     - Maps to key: e.g., "20-40_male", "under-20_female"
     - 3-second CONSENSUS WINDOW: collects 30 samples and takes majority vote
       to prevent misfires from momentary detections

  3. AD SELECTION (Rules Engine)
     File: backend/modules/ad_engine/selector.py
     - Reads rules.json (demographic key → .mp4 filename mapping)
     - Returns matching personalized ad URL for State 2

  4. NATURAL LANGUAGE (Hybrid QA / LLM)
     File: backend/modules/interaction/brain_engine.py
     - ProductQAEngine: pre-indexed product JSON, exact keyword matching (fast)
     - TinyLlama (llama-cpp-python): local LLM fallback for open-ended questions
     - Context loaded from product JSON files (brand, price, features, FAQs)

    Startup: run_adorix.bat automates:

1.9 CRUD OPERATIONS
---------------------

  CRUD operations exist across both repos:

  [adorix-webb – Web Platform]

  CREATE:
    - POST /api/contact → Creates a new contact inquiry (contact.controller.js)
    - Campaign Studio: Creates new ad campaign in Supabase
    - Clerk: Registers a new user account

  READ:
    - GET /api/user → Reads user profile data from Supabase (user.controller.js)
    - Dashboard: Reads analytics data from Supabase for display in Recharts charts
    - GET /api/contact → Reads submitted contact forms

  UPDATE:
    - PUT /api/user → Updates user profile settings
    - Campaign Studio: Edits existing campaign metadata (title, targeting, schedule)

  DELETE:
    - Campaign Studio: Deletes an ad campaign from Supabase
    - User profile deletion (via Clerk admin)

  [adorix-project – AI Kiosk]

  CREATE:
    - POST /api/sync → Pulls new ad files from Supabase and writes them to /ads/
    - Analytics module records new session data on each State 3 interaction

  READ:
    - GET /api/ads → Reads available .mp4 files in the /ads/ directory
    - AdSelector reads rules.json to query demographic-to-ad mappings

  UPDATE:
    - State machine updates system state (system_id, ad_url, mode) on transitions
    - rules.json is refreshed after each sync

  DELETE:
    - Old or expired ads removed from /ads/ directory during sync
